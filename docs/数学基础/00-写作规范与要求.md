# 数学基础整理项目 —— 写作规范与要求

这份文档记录了整个项目的固定语法规则，目的是后续继续整理新模块（或修改旧模块）时不用再重复说明一遍。**每次新开会话整理内容前，先看这份文档。**

> **内容取舍：不再做重点分类。** 项目早期用 🔑核心 / 🟡了解 / ⚪跳过 三档标签给每个小节标优先级，只详写"对具身智能有用"的部分。这套做法现已取消——目标改为**全面补习高中数学**，所有小节一律按同一标准完整整理：完整的概念讲解 + 公式推导 + 例题，不再因为"应试技巧、具身智能用不上"而精简或跳过任何内容。新写的模块不要再加优先级标签，标题就是 `## 一、xxx`；旧模块里残留的标签遇到时顺手去掉即可。

> **已发布的内容不擅自修改。** 一篇笔记发布（提交推送）之后，即使后来发现它违反本文件的某条规则，也**不要自己动手改**——先指出具体哪里违反了、给出修改建议，等用户明确要改再动手。没发布（还没 `git commit`）的内容不受此限，发现问题随时可以直接改。**每篇笔记写完、还没发布之前，对照本文件通读一遍自查**，尤其是下面这条最容易忘的规则。

> **具身智能相关的说明，只出现在开篇总览表的第三列，正文各节一个字都不能有。** 这条规则被违反过不止一次，每次的表现都是：本来该讲纯数学的段落里，突然插入一句"这在具身智能里对应……""在机器人学里用于……""这是……的地基/起点/来源"之类的话，或者干脆整段/整节内容都是拿一个具身智能场景（相机、机械臂、SLAM、点云）当例子在讲。自查时按下面的清单逐条过：
> - 全文搜索这些词，任何一处出现在表格之外，都是违规，要删或者把那句话里的应用说明部分去掉，只留数学内容：`具身智能`、`机器人`、`机械臂`、`相机`、`传感器`、`点云`、`SLAM`、`RANSAC`、`卡尔曼`、`旋转矩阵`、`四元数`、`碰撞检测`、`SDF`
> - 也要搜前向引用型的句式，同样只能出现在表格里：`后面用`、`后面在哪`、`后面推`、`第 N 行会用到`、`这是……的地基`、`这是……的起点`、`这是……的来源`
> - 如果一整个 `### 图示：xxx` 或某个知识点的配图和讲解，本身就是拿一个具身智能场景包装的（比如"针孔相机成像"当成相似三角形的示例），把它当成违规处理，不要因为"它同时也在讲数学"就放过——正文里但凡整段的叙事框架是具身智能场景，就要挪出去或者删掉，纯数学的推导可以留，但要去掉外层的应用包装（相机、光心、成像平面这类命名）
> - 表格第三列本身不受此限，那里就是专门写应用的地方，越具体越好

## 一、文件与目录结构

**所有笔记平铺在 `docs/数学基础/` 下，不要给每一篇单独建子文件夹**；全部笔记**共用同一个 `docs/数学基础/assets/`** 存放配图。

    docs/数学基础/
    ├── 00-写作规范与要求.md      ← 本文件
    ├── 学习路径.md
    ├── 01-代数变形.md
    ├── 02-....md
    └── assets/                   ← 所有笔记共用
        ├── 平方差的面积解释.svg
        └── ...

- `.md` 里引用图片仍然写相对路径 `assets/xxx.svg`，笔记和 assets 在同一层，路径不变。
- **图片文件名要能自解释**（写清楚画的是什么），因为所有笔记的图混在一个目录里，靠文件名区分归属。
- **注意校验脚本的用法变了**：`assets/` 由多篇笔记共用，"图片没被引用"这一项必须等所有 md 都扫完才能判断，所以**必须一次校验整个目录**（`"docs/数学基础/*.md"`），不能只传单个文件，否则会把别的笔记用的图误报成未引用。

## 二、每篇笔记的固定结构（从 `01-代数变形.md` 定型，后面一律照此写）

**文件名**：`NN-主题.md`，`NN` 是学习路径里的行号段（如 `01-代数变形.md`）。

**一级标题**：`# 具身智能数学基础(NN)：主题`。括号里的编号对齐文件名，冒号后面必须带主题名——否则侧边栏里一排都叫"具身智能数学基础(xx)"，分不清哪篇是哪篇。

**不要写目录**。VitePress 右侧自带大纲，正文里再放一份是重复。

**读者的使用方式是：先读笔记，读懂就过，读不懂才去看视频。** 所以**正文必须自足**——不能出现"这部分看视频"这种把责任推给视频的写法，视频只是兜底。

正文按下面的顺序写：

1. **h1 下面直接放总览表，中间不写任何引言**。"学习路径第几行、预计几小时"这类交代没有信息量，不要写。

2. **总览表**三列：`内容` / `必须掌握的` / `后面在哪用到`。
   - 第二列只列**必须掌握的**，可有可无的不要写进来
   - 第三列写清楚在具身智能里对应什么，写不出来的知识点就不该单独成节
   - **"后面在哪用到"只在这张表里写一次**。正文里不要再重复"这个后面推卡尔曼滤波要用""第 36 行会用到"之类的话——写一遍是信息，写两遍就是臃肿。正文只讲知识本身

3. **各知识点独立成节**，标题格式 `## 一、xxx`、`## 二、xxx`（中文数字编号）。
   - **开头直接写定义，不加 `### 是什么` 这类小标题**——二级标题下面第一段本来就是定义，再加小标题是废话
   - **三级标题只在真正需要分段时才用**，且要起有信息量的名字（`### 指数的三次扩展`、`### 配方法`、`### 唯一的大坑：约分会改变定义域`），不要用 `### 是什么`、`### 内容`、`### 说明` 这种占位标题
   - `### 图示：xxx`——能画图的一律画图（见第四节）。**图要直接画数学对象本身**（函数图像、几何图形），不要画"示意流程"去绕着解释；图下面用一两句话说明图上看到了什么，不要展开成一大段
   - **不写"易错点""常见错误""解题技巧"这类小节**。读者不做题，只需要知识本身；确实属于知识的部分（比如 $\sqrt{a^2}=\lvert a \rvert$ 要先判符号、矩阵不满足 $(AB)^n=A^nB^n$）直接并进对应的法则里说一句
   - `### 例题`——**默认不写**，见下

4. **只有"要分步展开才说得清"的证明才挪到 `## 推导与证明`一节**（位置在全部知识点小节之后、`## 对应视频`之前），**一两句话就能写完的证明留在正文原地，不要挪**——挪走后读者还得往下翻，对这么短的内容反而更麻烦。判断标准：写下来要不要分"第一步、第二步"这种结构，或者要不要用到辅助线/辅助量构造，需要就挪，不需要就留在原地跟结论写在一起。
   - 移走的证明，`## 推导与证明`内部用 `### ` 小标题对应正文里的结论（比如正文写"勾股定理"，这里就是 `### 勾股定理的面积证明`），方便按结论查证明；正文原地留一句"证明见后面"的指引。
   - **证明如果配了图，正文和 `## 推导与证明`里各放一份同样的图**——读者看证明时不用再往上翻找图。
   - **注意区分"证明"和"方法"**：证明是验证一个已经陈述的结论为真，符合上面的长度标准才挪；配方法、因式分解、待定系数法这类"怎么做"的算法/技巧本身就是要掌握的知识，不是对某个结论的证明，永远留在正文对应小节里，不移动。

5. **`## 对应视频`（放全文最后）**——见下。**不写小结**：知识点各节里已经把要点讲清楚了，再总结一遍是重复。

**行文要求：知识翔实，文字简练。** 公式、定义、法则、适用条件一条都不能少（翔实）；但铺垫、动机、感慨、"这一步很重要""这是最容易错的"这类话一律删掉（简练）。判断标准：删掉一句话之后，读者掌握的知识有没有变少？没变少就该删。

**内容取舍**：全面指的是**具身智能里用得到的全面**，不是教材大纲的全面。判断每一条要不要写，只问一句"后面哪一行会用到它"，答不上来就删。反过来，只要后面用得到，哪怕教材上是选学、甚至不在教材里（比如配方法在卡尔曼滤波推导里的作用），也要写足写透。

**`## 对应视频` 的写法**（放全文最后，不放开头）：

- **用缩进列表，不要用表格**。一级是知识点，二级是该知识点对应的视频
- 开头一句话交代用法："正文看得懂就跳过，卡住了再看对应那一段"，并给出真正值得看的合计时长
- 每条视频写成：`[P几 标题](带 ?p= 的链接)（时长）— 看不看、看哪段`
- **判断依据只有一条：这段内容对具身智能有没有用**，不是这一集讲得全不全，更不能照抄视频标题里的定位。这是踩过的坑：曾经按"覆盖度"把一集应试技巧课标成"主看"，被用户当场指出来
  - 一数、赵礼显这类都是**应试向 UP 主**，标题里出现"稳定得分""压轴""秒杀""技巧""自主招生"这些字眼，对应的基本是考试套路，默认标**跳过**
  - 同一集常是**前半原理、后半套路**，要写清看哪段、略哪段，不要整集一刀切
  - **判定为跳过的视频，直接不要列出来**。列一条又写着"跳过"，等于让人白读一遍——筛选的结果应该体现在列表里没有它，而不是列出来再否定
  - 哪些知识点**合集里没有对应视频**，在列表后面用一句话统一说明，不要给它们各占一个列表项
- 集数、标题、时长**必须联网核实**（打开 B 站页面读分 P 列表），末尾注明"取自 B 站页面，未逐集观看"

**例题的写法**（仅在用户要求时才写）：

- **分步骤写**，每步用 `**第一步，做什么。**` 开头，先说这一步的目的，再写式子
- 每一步的式子单独成行（行内公式 `$...$`，不要用 `$$`），不要把几步挤在一段话里
- **必须有验算那一步**，并说明为什么这么验（代一个特殊值、估算数值、代回原式都行）
- 有坑的地方要**明确点出来**（比如"这里是全篇最容易错的一步"），并解释错了会怎样
- 题目本身也能画图说明的，就在例题里再配一张图

**语气与篇幅**：面向的是成年自学者，不是中学生。可以直接说"这条必须背熟""这一步不要省"，但不要写成应试口诀。单篇控制在能一次读完的长度，超了就说明该拆成两篇。

## 三、Markdown 正文的数学公式格式（重要，反复踩过坑）

1. **所有数学公式必须用行内语法 `$...$`，绝对不能用独立成行的 `$$...$$` 块**。原因：语雀导入后，`$$` 块会导致公式居中显示（用户明确反对），且被怀疑会干扰语雀的大纲/标题解析器（曾导致标题在大纲中丢失）。哪怕是"重点公式想单独强调"，也要写成"用 `-` 项目符号包裹的一行行内公式列表"，不能用 `$$`。
2. **公式内的大于号、小于号，一律用 LaTeX 命令 `\lt` 和 `\gt`，不能用裸字符 `<` 和 `>`**。原因：语雀的导入器会把裸的 `<`、`>` 自动转义成 `&lt;`、`&gt;`，而这个转义发生在语雀内部导入阶段，KaTeX渲染时会直接把 `&lt;` 当成文本渲染出来（报"KaTeX parse error"），**这个问题无法通过在源文件里换用别的字符来"再次修复"**——因为源文件里写的已经是正确的字符了，问题出在语雀导入这一步。唯一稳妥的解决办法就是从一开始就用 `\lt`/`\gt`（纯字母命令，语雀不会转义）代替裸的 `<`/`>`。
   - 注意 `\le`、`\ge`（小于等于/大于等于）本身就是字母命令，不受影响，不用改。
   - 注意 `\lt`、`\gt` 后面如果紧跟字母（比如 `x\ltx_2`），会被解析成不存在的命令名，**必须保留空格**，写成 `x \lt x_2`。
3. **公式内的撇号一律用 `^{\prime}`，不能用字符 `'`**。这是和上一条完全同类的问题：语雀会把撇号 `'` 转义成 HTML 实体 `&#39;`，KaTeX 同样解析不了，报"非法 TeX 公式"。
   - 错误写法：`$f'(x) \gt 0$`、`$y'=2x$`、`$\angle A'$`、`$BA'=2R$`
   - 正确写法：`$f^{\prime}(x) \gt 0$`、`$y^{\prime}=2x$`、`$\angle A^{\prime}$`、`$BA^{\prime}=2R$`
   - 二阶导数写成 `$f^{\prime\prime}(x)$`。
   - **⚠️ 注意撇号不只出现在导数里**：几何题里的"点 A′、B′"（对称点、辅助点、平移后的点）同样会踩坑。这个坑犯过两次——第一次是导数模块的 `f'(x)`，第二次是向量模块正弦定理证明里的 `∠A'`，都是写的时候没想起来这条规则。
   - **归纳规律**：凡是"在 HTML 里有特殊含义、会被转义的字符"（`<`、`>`、`'`、`"`、`&`），都不能以字符形式出现在 `$...$` 里，必须换成对应的 LaTeX 命令。**不要靠记忆，靠第五节的校验脚本自动查。**
4. 允许使用的标准LaTeX命令：`\subseteq`、`\subsetneq`、`\cap`、`\cup`、`\complement_U`、`\varnothing`、`\mathbb{R}`（以及`\mathbb{N}/\mathbb{Z}/\mathbb{Q}`）、`\dfrac{}{}`、`\sqrt{}`、`\sqrt[n]{}`、`\le`、`\ge`、`\ne`/`\neq`、`\Rightarrow`、`\Leftrightarrow`、`\iff`、`\forall`、`\exists`、`\neg`、`\parallel`、`\perp`、`\triangle`、`\vec{}`、`\dot{}`（点积用 `\cdot`）、`\times`、`\angle` 等。
5. **不要用markdown代码围栏（三个反引号）包含竖式计算等内容**，尤其避免代码块里出现连续短横线（如 `-------`）作为分隔线——这会破坏语雀的解析器。这类内容改用行内格式，或用 `─`（制表符/box-drawing字符）代替短横线。整个项目目前的做法是：**正文里基本不使用代码围栏**。

## 四、SVG 配图规范（和 .md 正文的规则刚好相反，注意别弄混）

1. **SVG文件的文本内容里，`<`、`>` 必须使用XML实体 `&lt;`、`&gt;`，绝对不能用裸字符，也不能用全角字符 `＜`、`＞` 替代**。原因：SVG本质是XML，裸的 `<` 会被解析成标签开始符号，导致XML解析失败（已经用浏览器实测验证过，报 "StartTag: invalid element name" 错误）。**这一条只适用于SVG，千万不要把"正文改用\lt/\gt"的规则错误地应用到SVG文件上**——之前发生过一次把这条规则错误地应用到21个SVG文件上，导致XML解析全部损坏，后来才修复回来，用户对此明确纠正过，务必记住这个边界。
2. SVG里的HTML注释 `<!-- ... -->` 要保留字面的 `-->` 结尾，不能把注释里的 `>` 也转义成 `&gt;`（注释内容本来就不会被当成XML标签解析，不需要转义，转义反而会破坏注释本身的结束标记）。
3. **每个SVG创建/修改后，必须跑验证脚本**，确认三件事：
   - XML良构性：能被 `xml.etree.ElementTree.parse()` 正常解析（不会报parse error）
   - 视觉内容在viewBox范围内：所有 `circle/line/text/polygon/polyline/rect` 等元素的坐标，在累加所有祖先 `<g transform="translate(x,y)">` 偏移量之后，都落在声明的 `viewBox` 范围内（不会被裁切）
   - **文字的实际渲染宽度不超出viewBox**（见下一条，这是最容易漏掉的一项）
   - 脚本已固化在项目里：`_工具/validate_svg.py`（早期放在临时目录，会被系统清理，现已移入项目）
4. **⚠️ 文字溢出是本项目最高频的返工原因，必须专门检查**。教训：只检查文字的锚点坐标（x,y）是不够的——锚点在画布内，但一行长文字仍然会向右（或居中时向两侧）超出画布被裁掉。曾经因为漏掉这项检查，21个文件同时存在文字被截断的问题。
   - **宽度估算方法**：中日韩全角字符按 1.0×font-size 计算，英文/数字/半角符号按 0.55×font-size 计算。再根据 `text-anchor` 换算出实际占据的横向区间：`start` 是 `[x, x+w]`，`middle` 是 `[x-w/2, x+w/2]`，`end` 是 `[x-w, x]`。
   - **写图时的经验值**：font-size 13 的一行中文，超过约 40 个字就需要 620 以上的画布宽度；底部说明文字尽量控制在 30 字以内，超了就**拆成两行**（每行 y 相差 22~24），而不是硬塞一行。
   - **修复优先级**：短句超出一点 → 直接加宽 viewBox 和背景 `<rect>` 的 width（居中文字记得把 x 同步改成新的画布中心）；长段文字大幅超出 → 拆成多行更美观。
5. **⚠️ 文字（字母、数字、说明）绝对不能压在线条或图形上**，必须放在空白处。这是用户明确提过的要求，所有图一律照办。
   - **最小间距**：文字与任何线条、边框、曲线保持 **12 像素以上**的净空。坐标轴的刻度数字统一放在轴外侧 20~27 像素处（x 轴刻度放下方，y 轴刻度放左侧），不要贴着轴写。
   - **轴名与原点标记**：`x`、`y`、`O` 三个标记最容易压线。`x` 放在横轴箭头的**斜下方**，`y` 放在纵轴箭头的**右侧**，`O` 放在原点的**左下方**，都要留够 12 像素。
   - **曲线上的点如果要标注**，不要把文字直接写在点旁边，用一条**虚线引出**到空白区域再写，引线和文字都要避开曲线（先算出曲线在该高度的横坐标，确认文字起点在它右侧或左侧 20 像素以上）。
   - **实在避不开时**（图形太密），在文字下面先垫一个与背景同色的 `<rect>` 做白底，再画文字；但这是下策，优先靠重新布局解决。
   - 脚本查不出这一项（它只查是否超出画布），**必须靠 `qlmanage` 渲染后肉眼确认**。
6. **凡是要画真实数学曲线/函数图像的SVG（比如sin/cos图像、抛物线、椭圆、幂函数曲线等），必须用Python实际采样函数值算出坐标，再拼成 `<polyline points="...">`，不能靠手绘的贝塞尔曲线去"估计"形状**——手绘估计曾多次导致"曲线根本没有经过声明的点"这类错误（比如说曲线过(1,1)点，但实际画的曲线根本没经过那里）。
7. **⚠️ SVG里的根号绝对不能直接用 `√` 字符，必须用 `<path>` 手工画**。这是本项目反复出现的老问题（基本不等式、辅助角公式、点到直线距离、数轴上找√2 等多张图都犯过）。原因：Unicode 的 `√`（U+221A）只是一个"钩"，**它没有上面那条横线（被开方数上方的横杠/vinculum）**，所以 `√(ab)`、`√2` 渲染出来都是残缺的根号，看着就像写错了。写 `√(a²+b²)` 加括号也只是勉强能读，不是正确的数学排版。
   - **正确做法**：把"被开方数"单独作为一个 `<text>`，再用一条 `<path>` 画出"钩 + 覆盖被开方数的横杠"。以被开方数文字左端 `xr`、基线 `y`、字号 `fs` 为基准：

     `<path d="M (xr−0.62fs) (y−0.46fs) L (xr−0.37fs) (y−0.14fs) L (xr−0.11fs) (y−1.02fs) L (xr+W+0.2fs) (y−1.02fs)" fill="none" stroke="颜色" stroke-width="0.095fs" stroke-linejoin="round" stroke-linecap="round"/>`

     其中 `W` 是被开方数文字的估算宽度（算法见本节第 4 条）。四个点依次是：钩的起笔、钩底、钩顶、横杠右端。
   - **前缀要留间隙**：如果根号前面还有文字（比如 `CD=`），前缀文字宽度要单独估算，再留约 `0.14fs` 的间隙才开始画钩，否则钩会和前面的 `=` 叠在一起。
   - **字符宽度估算要分类**：括号/斜杠/空格这类窄字符约 `0.32fs`，字母数字约 `0.57fs`，运算符（`=` `+` `≥` 等）约 `0.62fs`，中日韩全角字符按 `1.0fs`。用统一系数会导致间距忽宽忽窄。
8. **常用图形的画法约定**（跟教材保持一致，用户对此有明确偏好）：
   - **数轴上表示不等式解集（用户指定的画法，必须照这个来）**：这是国内教材求交集的标准画法，每个不等式画成一条"横线 + 折钩"，交集画在数轴本身上。具体规则：
     - **一个不等式一条横线**，画在数轴上方，横线沿解集的方向延伸（`x \lt a` 向左，`x \gt a` 向右），到端点处**直角折下来**，竖线一直落到数轴上——整体像一个折钩。用一条 `<polyline>` 画完，不要拆成两段。
     - **多个不等式用不同颜色、不同高度**（相差 40 像素左右），横线可以左右重叠，靠高度区分。每条横线在它**自由的那一端**标上对应的不等式（如 `x &lt; 3`），标签与横线留 12 像素净空。
     - **端点画空心圆**（取不到）或**实心圆**（取得到），圆心落在数轴上，**描边颜色跟随它所属的那条横线**，填充白色，半径 8 左右。
     - **交集画在数轴本身上**：用醒目颜色（绿色）的**粗线段**（stroke-width 5 以上）压在数轴上，正是各条横线水平重叠的那一段。要先画绿线再画端点圆，圆才不会被盖住。
     - **端点处不要再画刻度短线**，让位给圆圈；其余刻度正常画。刻度数字统一放数轴下方 36 像素处，端点对应的数字用它那条线的颜色。
   - **面积法证明公式**（如平方差、完全平方）：要把"剪"和"拼"两步都画出来——剪的那条线和拼的那条线都用**同色虚线**标注，两块图形用**不同填充色**并编号 ①②，这样左右两图的对应关系一眼可见。只画"前"和"后"两个静态图形是不够的。
   - **被挖掉的点、被去掉的部分**：一律用**灰色虚线框**或**空心圆**表示，不要直接省略不画。
9. 三维/立体几何类的配图，统一采用固定的斜二测投影公式做手工3D效果（避免用真正的透视投影，保持和教材风格一致）：
   - 投影公式：`screen_x = ox + (x*xs*(-cos30°) + y) * scale`，`screen_y = oy + (x*xs*sin30° - z) * scale`，其中 `xs≈0.55` 是x轴的压缩系数
   - 同一个模块内的多张3D图尽量复用同一套投影参数，保持视觉一致性

## 五、每篇笔记完稿前必须跑的验证清单

### 第一步：跑两个校验脚本（已固化在项目 `_工具/` 目录，不用每次重写）

**在仓库根目录（`具身智能/`）下执行**，`_工具/` 就在根目录里，笔记在 `docs/数学基础/` 下面：

    python3 _工具/validate_md.py  "docs/数学基础/*.md"
    python3 _工具/validate_svg.py "docs/数学基础/assets/*.svg"

  **md 那条必须用 `*.md` 通配一次跑完整个目录**，原因见第一节：assets 是共用的，只传单个文件会误报未引用。

- **`validate_md.py`** 检查：`$$` 公式块、代码围栏、**公式内的裸 `<` `>` `'` `"`**、图片引用与实际文件是否一一对应、目录与正文标题是否一致。
- **`validate_svg.py`** 检查：XML 良构性、图形坐标越界、**文字渲染宽度溢出**、裸露的 `√` 字符。

两个脚本都必须输出"0 个有问题"。

**⚠️ 必须用脚本，不要临时手写 grep 检查**：在 shell 里对 `$`、`'` 做转义极易出错——曾经因为引号转义问题，明明有 4 处违规却报告"0 处"，导致问题一直漏到用户那里才被发现。脚本用 Python 正则处理，没有这个坑。

### 第二步：脚本查不出来、必须人工确认的部分

1. **关键图渲染肉眼检查**：`qlmanage -t -s 900 -o . 文件.svg` 生成 PNG 后实际看一眼。脚本能查坐标和宽度，但查不出"线条重叠""标签压住曲线""根号横线位置偏高偏低""弧线画在了错误的位置"这类视觉问题——含公式、含根号、含多条曲线、含角度标记的图尤其要看。
2. **数学内容本身是否正确**：图里画的曲线/角度/线段，是不是真的等于它标注的那个量。凡是涉及真实几何的，先用 Python 把坐标算出来并**打印校验值**（比如"点积应为0""两种算法结果应相等"），确认无误再写进 SVG。
3. **小节标题的编号顺序**有没有漏、有没有因为插入新小节而错位（目录里的锚点链接要跟着一起改）。

全部通过之后才能算模块完成。
